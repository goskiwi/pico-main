# 首轮真实评测失败原因复核（2026-09-05）

本次只分析已保存的四次试跑，并额外执行四次容器内公开测试检查；没有重新调用付费模型，没有改写任何候选补丁或原始成绩。

## 结论

0/4 由不同原因叠加产生：评测没有接入已有 Runtime 验证闭环、模型对跨阶段／跨层接口语义的修复不正确、模型调用耗时和异常，以及少量工具协议错误。当前证据不支持“RepoMap 本地计算拖慢了整个系统”或“压缩丢失上下文导致失败”的解释。

## 1. 评测未接入 Runtime 的验证闭环

`scripts/run_repo_eval.py` 创建 `PicoConfig(mode="auto", **BUDGET)`，没有设置 `verification_command`。`RunLifecycle._task_contract()` 因而将 `verify_changes` 设为 false。四条持久 Run Log 的首个 TaskContract 均确认了这一点，且任务提示明确告诉模型没有测试反馈。

这是上一轮评测接法的限制，不是 Pico 没实现 CompletionController 或 verifier。因此本轮 pytest 的 `completed` 仅表示满足这套无验证协议的完成条件，不能表示通过实际功能验证。

额外的公开测试检查使用全新容器、历史 base commit 和原始候选补丁；不应用数据集的 `test_patch`：

| 公开测试 | 原代码 | 模型候选补丁 |
|---|---|---|
| pytest 的 `test_caplog_captures_for_all_stages` | 通过 | 失败 |
| Sphinx 的原有 `tests/test_ext_autodoc_configs.py` | 14 项通过 | 14 项通过 |

结果存于 `artifacts/repo-eval-failure-analysis/public-tests.json`，对应 `.log` 文件保留完整输出。

这证明公开验证能拦住本次 pytest 回归；它不能证明模型拿到反馈后一定会修好，也不能保证 Sphinx 的新增需求得到满足。

## 2. pytest：把两种不同的状态转换混为一谈

两组都把 `LogCaptureHandler.reset()` 内的 `self.records = []` 改成 `self.records.clear()`。

原实现中，各测试阶段会把当时的 records 列表放入 stash。进入下一个阶段时 reset 创建新列表，从而让 setup、call、teardown 各自保留独立记录。

模型希望解决的是用户 `caplog.clear()` 后的引用同步问题，却改动了所有阶段都调用的 reset。就地清空让阶段间复用了同一个列表，结果 setup 查询读到了 call 阶段日志。

独立测试中的实际差异：`caplog.get_records("setup")` 预期 `['a_setup_log']`，实际得到 `['a_call_log']`。原有公开回归测试也能复现，不需要隐藏断言。正确的设计方向应区分“阶段切换创建新列表”和“当前阶段清空已有列表”，而不是全局替换 reset 的行为。

两组都读取了相关实现和测试，开启组首轮就读取了阶段切换附近代码。因此不能把错误完全解释为没有检索到目标上下文；已有上下文并未转化为正确的状态语义判断。

关闭组还发生了一次 revision 抄写错误：期望值末尾为 `...3101`，工具读取的真实 revision 末尾为 `...3106`。修改前没有成功写操作。这是模型复制 revision 时出错，不是已经证明发生了外部并发编辑。Runtime 正确拒绝了它，模型重新读取后继续。

开启组 5 次逻辑调用，关闭组 9 次；差异包含目录／符号定位和 revision 修复回合。因此单题 Token 差值不能单独归因为 RepoMap，也不能把两个失败答案的用量差称为修复效率提升。

## 3. Sphinx 开启组：格式化接口改错，且时间耗在模型调用边界

最终补丁只改 `DocstringSignatureMixin._find_signature()`，把带括号、返回类型和换行的多个完整签名拼进原本的 args 字段。下游 `Documenter.format_signature()` 仍执行 `args = "(%s)" % self.args`，导致额外括号和错误的签名结构；续行反斜杠也没有得到正确处理。

独立测试实际输出包含 `E((foo: int, bar: int, baz: int) -> None \\)`，而预期是两条正确排列的重载签名。模型曾读取过下游格式化实现，仍没有同步处理接口语义。

原有公开测试文件的 14 项测试全部通过，但独立验收中加入的新覆盖失败。这说明“现有测试通过”只能避免部分回归；新行为还需要来自需求的复现场景和新增覆盖。不能预先断言接回旧测试反馈就能解决此题。

耗时记录：

| 试次 | 总推理秒 | 逻辑模型调用累计秒 | 其余耗时秒（差值） |
|---|---:|---:|---:|
| pytest 开 | 111.773 | 110.228 | 1.545 |
| pytest 关 | 178.240 | 178.027 | 0.213 |
| Sphinx 开 | 600.028 | 598.187 | 1.841 |
| Sphinx 关 | 267.918 | 267.643 | 0.275 |

这里的模型调用边界包含本机组装／解码、传输、可能的 HTTP 重试和远端处理，不能再细分为排队、推理或网络时间。它足以说明本轮没有观察到 RepoMap 的本地索引耗时主导 600 秒。

Sphinx 开启组第 4、5 次调用分别耗时 122.095、121.720 秒；前五次调用共约 329 秒，尚未执行首次修改。随后多次编辑，最终在第 11 次调用期间耗尽剩余预算。没有充分依据仅通过增加工具轮数来解决这一超时。

## 4. Sphinx 关闭组：模型调用异常的具体根因缺失

第 5 次逻辑调用耗时 180.007 秒，随后抛出 RuntimeError；与脚本配置的单次请求总时限 180 秒吻合。前四次调用共约 87.6 秒，模型尚未形成补丁。

旧试跑只记录了异常类型，没有保存异常消息、HTTP 状态或每次传输尝试。因而只能确认模型调用未正常返回，不能断言是限流、网关故障、网络超时或模型服务内部错误。Provider 的单次逻辑调用内部最多允许三次传输尝试；这些尝试当时没有逐次记录。

后续脚本已经保存脱敏异常消息，但这不能补回此次丢失的信息；原始试次没有重跑或补写。

## 5. 工具交互存在可改进的摩擦

- Sphinx 关闭组曾在一轮请求 5 个观察调用，超过明确说明的上限 4；整批被拒绝，产生 5 个失败 Call 结果。不是连续出现 5 次批量失败。下一轮模型改为 4 个调用后正常执行。
- Sphinx 开启组使用了 `add_directive_header(` 和包含 `\n` 的搜索模式。前者没有转义括号，后者要求当前工具没有启用的多行模式，均被 rg 拒绝。
- 当前 SearchArgs.pattern 没有说明正则语义，工具描述只写了 rg／fallback。这是可以改进的接口说明问题；可明确单行正则规则，并考虑显式的字面量搜索选项。
- revision 检查和批量边界都按设计拒绝了不合法调用，不应为了消除这些失败记录而移除已有检查。
- 四次试跑均没有 compaction 事件，本轮不能用来判断压缩方案的收益，也没有证据把这些失败归因为压缩丢失上下文。

## 优先级

1. 先纠正评测协议：在容器中接回公开回归测试作为 Runtime verifier，独立验收测试继续只用于最终判分。保持两组模型与预算相同，将新协议和旧协议分别报告。
2. 保留并完善模型请求的失败类型和耗时诊断；不凭当前聚合计时猜测服务商原因，也不把异常试次当作 RepoMap 因果收益。
3. 明确搜索工具的正则／字面量语义，减少无效调用。
4. 对新增行为建立复现与验证路径。确认这些问题处理后再扩大样本，而不是直接用更大的轮数和超时掩盖问题。
