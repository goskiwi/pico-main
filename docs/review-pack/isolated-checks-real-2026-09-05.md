# 可选复现工具与一次真实模型验证（2026-09-05）

本轮补充 `run_check` 并完成本地验收，随后只运行一个真实开发任务，没有批量重跑。
结果：最终候选通过既定独立验收，也通过上轮发现的“调用方保存 setup 引用”补充回归。
这个已审查案例不是盲测样本，结果不能用来推断总体成功率或 RepoMap 收益。

## 新能力

- 只有显式注入隔离执行器时，Code／Auto 才有 run_check，Ask 不暴露；普通 CLI 默认不安装。
- 模型可运行临时 Python／pytest 片段；宿主源码和正式测试不会被这些片段改动。
- 参数最多 16,000 字符，默认 30 秒、上限 60 秒，受 Run 剩余时间与取消约束。
- 诊断输出最多保存 256 KiB；正常结束、超时、取消和输出超限后清理本次容器。
- 检查必须独占一轮；其结果不能替代固定 verifier 或独立验收。

## 本地验证

通过实际工具调用和 Docker 对照，原代码／参考修复通过引用检查，上轮候选失败，宿主文件保持不变。
另外验证了凭据隔离、文件隔离、超时、父级取消、输出上限、退出码和容器清理；容器内独立 timeout
也在不依赖 Runtime 父进程的条件下验证。普通回归 242 项通过；5 项 Docker 集成用例显式执行通过。
这些测试使用预设动作或直接调用执行器，不计为 LLM 成绩。

## 真实模型实际做了什么

模型使用 `gpt-5.6-luna`，同一历史 base commit、Auto、RepoMap 开启、600 秒预算，未收到补充回归的
测试代码。原始问题描述和通用工具说明中没有提供该边界检查的实现。

1. 模型首先尝试让 reset 就地清空列表，并用一次 Python 诊断验证“reset 保持列表身份”。诊断通过，
   但它验证的是一个错误的设计假设，随后公开回归仍失败。这说明模型自编检查不能独自充当验收。
2. 收到公开测试的真实失败反馈后，模型恢复 reset 的原行为，把就地清空放到 LogCaptureFixture.clear()
   中。最终补丁只改动该方法：清空 handler.records，并重新初始化日志文本流。
3. 模型主动运行第二次诊断：先保存 setup_records，再 reset 到新阶段，检查旧列表仍保留 setup
   日志、当前列表接收 call 日志，并检查当前列表清空后的同步。此诊断通过。
4. 第二次诊断直接测试了 handler 的阶段切换，但用局部操作模拟了 clear，并没有完整调用
   caplog.clear()。因此我们仍执行固定公开测试、独立验收和完整 fixture 形式的补充回归。
5. 公开回归 15 项通过；独立验收的 1 项 FAIL_TO_PASS 和 15 项 PASS_TO_PASS 通过；
   保留旧 setup 引用的补充回归也通过。

这次确认的是：模型确实使用了新增能力，最终修改通过了已明确列出的检查范围。
不宣称不存在其他未覆盖的问题，也不以两次不同协议的运行比较效率提升。
