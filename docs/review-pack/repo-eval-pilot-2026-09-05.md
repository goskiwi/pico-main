# 真实仓库评测：准备结果与首次试跑（2026-09-05）

12 个真实历史问题已完成源码准备与容器验证，其中 11 个在本机可判分。
首次对照只运行其中 2 题，每题 RepoMap 开、关各 1 次，共 4 次真实模型试次；独立测试结果为 **0/4 修复成功**。
这不是 11 题全量成绩，也没有证据支持 RepoMap 提升修复成功率。

## 本次协议

- 模型：`gpt-5.6-luna`，温度 `0`。
- 每试次 32 个 Agent Turn、64 次工具执行、600 秒 Runtime 预算、每次最多输出 4096 Token。
- 上下文上限 65536 Token；两组压缩参数相同，RepoMap 开组预算 1200 Token。
- 每题每组使用独立源码 checkout 和 Session；两题交替开／关组运行顺序。
- Auto、单 Agent、无 Shell；**本次未配置 Runtime 内部 verifier，模型不获得测试反馈，统一离线判分**。
- 使用官方 SWE-bench 4.1.0 的测试脚本、解析器和实例镜像，容器禁网、不挂载主机目录、不传入 API key。
- 只把数据集指定的 FAIL_TO_PASS 与 PASS_TO_PASS 条件当作独立判分依据，不声称全仓库所有测试都通过。
- 每个作答试次人工干预为 0；不包含环境准备和评测脚本开发工作。
- 部分环境准备与试跑同时进行，本轮耗时仅供诊断，不作为严格的性能结论。

## 已有证据支持的失败分析

**pytest-10051：两组生成同一错误补丁。** 两组都把 `LogCaptureHandler.reset()` 中的 `self.records = []` 改成 `self.records.clear()`。独立测试仍未通过 `test_clear_for_call_stage`，并破坏了 `test_caplog_captures_for_all_stages`。修改影响了阶段间共享记录的生命周期；仅在 reset 中就地清空列表不足以正确实现用户清理与阶段切换两种语义。

开启组使用 5 次逻辑模型调用，关闭组使用 9 次，完整上报 Token 相差 37,781。但两组都失败，不能把这个差值写成“修复效率提升”。当前协议没有让模型在提交时看到已有回归测试的失败反馈。

**Sphinx-7748：两组失败条件不同。** 关闭组第 5 次逻辑模型调用耗时约 180 秒后抛出 RuntimeError，未生成补丁；该次调用没有返回用量。首次试跑版本没有保存异常消息，因此不能进一步确定 HTTP 状态或根因。开启组完成了 4 次代码修改，随后达到 600 秒 Runtime 上限；保留的最终补丁仍未通过两项目标测试。

不能用这一对结果证明 RepoMap 帮助或拖慢修复。当前脚本已补充脱敏异常消息记录，供下一轮诊断；本轮原始记录和补丁没有补写、修改或重跑挑选。实际作答时的源码保存在运行目录内的 `runtime-source.zip`。

- 保留但暂不计分：Requests-2931。参考补丁仍不能通过两项连接超时回归测试，禁网环境实际返回 Network is unreachable；另有已收集测试报告 fixture 错误。这是参考修复验证中发现的环境问题，未让 Pico 作答后再换题。

## 下一轮应优先解决什么

1. 为实际 Runtime 接入容器内的公开回归测试反馈，同时保持新增独立测试不可见。将这一轮记录为新的实验协议，避免和本轮无反馈结果混为一组。
2. 利用新增的脱敏异常消息定位模型调用失败，不把请求异常直接归因为 RepoMap。
3. 再用同一模型、同一预算扩大到 11 道可判分任务，并做重复试验。两题单次试跑不足以支持总体收益或统计显著性。
